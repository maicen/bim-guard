# **Software Requirements Specification: ISO 19650 Compliance Engine for BIM-Guard**

## **Architectural Context and Baseline System Assessment**

The open-source platform BIM-Guard provides automated code compliance auditing, OpenBIM model inspection, and regulatory rule extraction[^1]. Its software architecture is organized around a decoupled service paradigm consisting of a Python FastAPI backend operating as an Asynchronous Server Gateway Interface (ASGI) service and a Single-Page Application (SPA) frontend built with Vite, Svelte 5, and Tailwind CSS[^2]. The underlying parsing and validation core relies on IfcOpenShell for Industry Foundation Classes (IFC) processing, buildingSMART Information Delivery Specification (IDS) evaluation, the buildingSMART Data Dictionary (bSDD) REST client, and the ThatOpenCompany Web-IFC viewport for geometric visualization[^2]. Persistence, relational integrity, and document storage are managed via Supabase PostgreSQL, which utilizes Row-Level Security (RLS) policies[^2]. Automated rule generation leverages LiteLLM across multiple foundation model providers, supported by web retrieval mechanisms[^2].

While BIM-Guard possesses analytical capabilities for domain-specific engineering checks—such as seismic clearance validation (GC-001) and atmospheric pipe corrosion risk assessment (CC-001)[^2]—it currently functions as an isolated quality gate rather than an integrated information management environment[^2]. To transition into full compliance with the ISO 19650 standard series ("Organization and digitization of information about buildings and civil engineering works, including building information modelling (BIM) — Information management using building information modelling"), the platform must expand its functional boundaries[^4]. This requires adopting the structured management processes defined across ISO 19650-1 (Concepts and Principles), ISO 19650-2 (Delivery Phase of Assets), ISO 19650-4 (Information Exchange), and ISO 19650-5 (Security-Minded Approach to Information Management)[^4].

The transition demands that BIM-Guard evolve from an ad-hoc checker into an authoritative digital delivery gatekeeper capable of enforcing Common Data Environment (CDE) state machines, multi-tier information exchange verification, decoupled metadata integrity, and entity-level access security[^3].

## **Information Container Identification and Metadata Specification (ISO 19650-2)**

ISO 19650-2 mandates that every distinct information container maintained within a CDE—such as IFC models, drawing packages, calculation sheets, and specification documents—possess a unique identification string defined by an agreed project naming convention[^3]. A critical defect in historical information management implementations has been the embedding of transient lifecycle attributes (such as approval status and revision indexes) within the physical file name[^11]. This practice results in broken hyperlinks, orphaned file dependencies, and synchronization failures across distributed federated systems[^4]. In full compliance with ISO 19650-2, BIM-Guard enforces the absolute decoupling of container identifiers from operational metadata[^11]. The physical container name remains immutable across its operational lifespan, while revisions, status codes, and classifications are managed exclusively through database-backed metadata schemas[^11].

The file naming engine implements the widely adopted National Annex standard structure, requiring seven distinct fields delimited strictly by a hyphen-minus character (-)[^11]. Under this standard, internal field values must not contain punctuation marks, spaces, symbols, or underscores[^12].

The metadata attached to each container in the Supabase PostgreSQL data store must track the exact status and revision history without altering the stored container key[^2]. The revision numbering engine enforces a strict two-tier syntax[^11]. During preliminary iterations within the Work in Progress state, the revision is formatted as Pnn.nn, where P signifies preliminary, the first two integer digits denote the target formal revision, and the two suffix digits represent internal task-team development cycles (for example, P01.01)[^2]. When a container successfully traverses the verification gate into the Shared state, the internal suffix is dropped, locking the revision identifier to Pnn (such as P01)[^6]. If the container is subsequently authorized for contractual publication, the revision prefix transitions to Cnn (such as C01), signifying contractual baseline validity[^11].

Suitability codes reflect the specific authorized business use of the container and are constrained by the container's active state[^11]. The system permits status codes S1 through S5 exclusively within the Shared state[^11]. Specifically, S1 authorizes the container for coordination across design disciplines, S2 provides information for reference only, S3 designates submission for multidisciplinary review and comment, S4 signals formal submission for lead appointed party stage approval, and S5 indicates submission for appointing party acceptance[^11]. Within the Published state, only contractual codes are permitted, including A1 through An (indicating authorization for construction stages, regulatory sign-off, or procurement) and B1 through Bn (indicating partial sign-off with non-blocking reservations)[^11]. Containers situated within Work in Progress are restricted to the default non-authorized code S0[^11].

## **Common Data Environment Workflow and Gated State Machine Controls**

ISO 19650-1 and ISO 19650-2 establish that an information container must reside within exactly one of four discrete CDE workflow states at any point in its existence[^3]. Progression between these states is governed by formal transition gates that prevent unauthorized dissemination and enforce explicit verification, approval, and authorization steps[^3].

The lifecycle begins in the Work in Progress (WIP) state, which represents the private drafting domain of a specific appointed task team[^3]. Here, information is authored and iterated without exposing intermediate design discrepancies to external project participants[^3]. Status codes are locked to S0, and revision numbering progresses through internal increments (P01.01, P01.02)[^2]. Task team members maintain read, write, and soft-deletion permissions within their isolated tenancy[^3]. External project participants, including the lead appointed party and appointing party, are barred from accessing WIP containers[^3].

Transition Gate 1 (Check / Review / Approve) mediates the boundary between Work in Progress and the Shared state[^3]. To initiate Gate 1 promotion, the originating task team submits the container to BIM-Guard's automated pre-flight gateway[^2]. The orchestrator validates file naming conformity, schema integrity, and initial Level of Information Need compliance[^2]. Upon passing these automated checks, the task team lead must digitally record an approval event, which generates a cryptographic log entry[^3]. BIM-Guard then advances the container state to SHARED, increments the revision metadata to the formal preliminary issue (dropping the decimal suffix to yield P01), and assigns an appropriate suitability code (typically S1 for coordination or S2 for information)[^6].

The Shared state serves as the collaborative coordination plane[^3]. Here, information is accessible to all appointed project participants to enable multi-disciplinary federation, clash detection, and engineering reviews[^3]. Containers in the Shared state remain non-contractual[^11]. Permissions for all appointed participants are strictly read-only; editing or direct overwriting of shared containers is prohibited[^3]. If a task team must rectify a coordination defect identified in the Shared state, the container is not modified in place; instead, a new revision cycle is initialized in WIP (for instance, P02.01), leaving the historical Shared record intact[^6].

Transition Gate 2 (Authorize / Accept) governs the progression from the Shared state to the Published state[^3]. This milestone signifies that the coordinated information delivery has undergone complete multidisciplinary federation, clash resolution, and compliance evaluation[^3]. The Lead Appointed Party verifies that the deliverables fulfill the Master Information Delivery Plan (MIDP), while the Appointing Party formally accepts the deliverable against the project Exchange Information Requirements (EIR)[^4]. BIM-Guard executes comprehensive automated compliance auditing—including spatial code rules, material durability algorithms, and full IDS validation[^2]. When all criteria pass and formal digital authorization is recorded, the container transitions to PUBLISHED[^3]. Its revision rolls to contractual status (C01), and its suitability code transitions to a definitive stage purpose (such as A1 or A2)[^11].

The Published state contains authorized, legally binding project outputs used for statutory approvals, procurement, fabrication, and physical construction[^3]. Immutability is enforced at the database and object-storage tiers: PostgreSQL triggers reject any update or deletion queries targeting published records[^2]. When an asset lifecycle stage concludes, or when a published deliverable is superseded by an authorized design alteration, the container moves across Gate 3 into the Archived state[^3]. Archiving maintains an immutable historical audit record, providing a forensic trail for post-occupancy dispute resolution, legal defensibility, and long-term asset management in accordance with ISO 19650-3[^3].

## **Information Exchange, Verification, and Validation Framework (ISO 19650-4)**

ISO 19650-4 introduces a formal methodology for executing and evaluating information exchanges across the asset lifecycle[^7]. The standard draws an essential distinction between verification and validation[^7]. Verification evaluates whether the technical payload of an information container adheres to defined syntax, schema, file structure, and standardized codification rules[^7]. Validation evaluates whether the informational content satisfies the specific operational, geometric, and semantic requirements defined by the appointing party for a particular delivery milestone[^7].

BIM-Guard executes automated information exchange evaluations via a four-tier processing pipeline[^2]. This pipeline runs asynchronously upon container ingestion and produces verifiable metrics that directly govern CDE gate clearances[^2].

| Evaluation Tier                           | Functional Classification | Technical Mechanism and Engines                                                                                                                        | Deterministic Pass/Fail Criteria                                                                                                  | Applicable Standards                            |
| :---------------------------------------- | :------------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------- |
| **Tier 1: Syntactic Integrity**           | Verification              | Low-level lexical parser evaluating ISO 10303-21 STEP physical file grammar, schema version header (IFC2X3, IFC4, IFC4.3), and GUID string syntax[^2]. | Zero parsing syntax errors; exact 22-character base64 GUID formatting across all entity records; single project root element[^2]. | ISO 10303-21, ISO 16739-1, ISO 19650-4 §5.2[^8] |
| **Tier 2: Schema & Delivery Spec**        | Verification              | Automated execution of buildingSMART Information Delivery Specification (IDS 1.0) XML contracts using ifcopenshell.ids[^2].                            | All mandatory entity, classification, material, property, and relation facets resolve within tolerance thresholds[^2].            | buildingSMART IDS 1.0, ISO 19650-4 §5.3[^8]     |
| **Tier 3: Semantic Conformance**          | Verification & Validation | Automated resolution of classification parameters and property set dictionaries via the buildingSMART Data Dictionary REST API[^2].                    | Property set assignments, data types, and enumeration values conform to official bSDD domain definitions[^2].                     | ISO 12006-3, ISO 19650-4 §5.4[^8]               |
| **Tier 4: Engineering & Code Compliance** | Validation                | Native BIM-Guard physics and regulatory engines: GC-001 (seismic bracing clearances) and CC-001 (corrosion galvanic compatibility)[^2].                | Zero non-exempt physical clashes, structural clearance violations, or galvanic degradation hazards[^2].                           | ASCE 7-22, ISO 9223, ISO 19650-4 §5.5[^2]       |

The cumulative outcomes across all four tiers determine the formal exchange decision disposition[^15]. If Tier 1 or critical Tier 2 IDS checks detect defects, the exchange is designated as REJECTED[^8]. The container is quarantined within WIP, promotion across Gate 1 is halted, and an exportable BCF topic archive is compiled[^2]. If all Tier 1 and Tier 2 criteria are satisfied, but Tier 3 or Tier 4 checks flag non-critical warnings, the exchange is categorized as ACCEPTED_WITH_COMMENTS[^8]. Under this status, the container advances to the target state, but tracking issues are registered via the BCF REST API, requiring resolution before the subsequent milestone[^2]. When all checks pass without exceptions, the exchange achieves an ACCEPTED status, clearing the container for progression across the active gate[^3].

To facilitate multi-disciplinary issue resolution, every detected non-conformance is transformed into a structured BCF v3.0 topic[^2]. The engine extracts the camera viewpoint, orthogonal clipping planes, and globally unique identifiers (GUIDs) of failing IFC entities directly from the model[^2]. It attaches the precise clause violation report, classification reference, and required remediation instructions, allowing lead designers to pull the issue context directly into desktop authoring software[^2].

## **Security-Minded Information Management Architecture (ISO 19650-5)**

ISO 19650-5 establishes principles for safeguarding sensitive digital engineering data against compromise, loss, and unauthorized dissemination[^9]. Digital models of built assets frequently incorporate Sensitive Commercial Information (SCI) or Sensitive Security Information (SSI), such as the layout of critical building utilities, telecommunications nodes, detention areas, secure vaults, and perimeter surveillance systems[^9]. In accordance with ISO 19650-5, BIM-Guard implements a comprehensive security governance framework combining security triage, Attribute-Based Access Control (ABAC), runtime geometric and semantic redaction, and an immutable cryptographic audit ledger[^9].

The security triage engine evaluates containers and internal IFC model structures during ingestion, assigning appropriate security clearance thresholds based on project security plans[^17].

| Security Classification                | Information Scope and Asset Typology                                                                                         | Technical Access Restriction Mechanism                                                      | Authorized Project Roles                                              |
| :------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------ | :-------------------------------------------------------------------- |
| **Level 1: Public / Open**             | Architectural massing, general exterior envelopes, published planning submittals[^9].                                        | Unrestricted authenticated read access; visible in common federation models[^3].            | All authenticated project users and public stakeholders[^3].          |
| **Level 2: Commercial Sensitive**      | Bill of quantities, unit cost schedules, contractor trade pricing, proprietary equipment specifications[^9].                 | Attribute-level masking within the API; stripped from non-commercial federated exports[^2]. | Appointing Party, Commercial Lead, Quantity Surveyors[^4].            |
| **Level 3: Infrastructure Restricted** | Primary MEP risers, high-voltage distribution networks, primary structural load transfer joints[^9].                         | Model segregation; access granted strictly via project role assignment[^9].                 | Lead Appointed Party, Appointed Lead Engineers[^4].                   |
| **Level 4: High Security Restricted**  | Security operations centers, access control circuits, custodial locks, executive protection zones, detention perimeters[^9]. | Dynamic geometric and semantic redaction via IfcOpenShell streaming filter[^2].             | Appointing Party Security Manager and Vetted Security Task Teams[^4]. |

When a project participant accesses an IFC container via direct file download or streams it into the Web-IFC viewer, BIM-Guard's sanitization service checks the user's cryptographic security clearance against the sensitivity tagging of the model elements[^2]. If a user lacking Level 4 clearance requests a model containing restricted entities, the service sanitizes the payload on the fly[^2]. The streaming pipeline prunes the associated IfcProduct entities, removes their geometric representations from the product tree, strips sensitive property sets (such as Pset_SecurityProperties), and unlinks related relationship records (IfcRelDefinesByProperties, IfcRelContainedInSpatialStructure)[^2]. This guarantees that unauthorized users receive a structurally and coordinate-consistent IFC model for coordination without exposing protected architectural layouts[^3].

To enforce non-repudiation and meet regulatory auditing requirements, every container transaction—including uploads, gate evaluations, streaming sessions, redactions, and file downloads—is recorded in an append-only audit ledger[^3]. Each log entry captures the timestamp, authenticated actor identifier, source IP address, action performed, and the SHA-256 binary hash of the affected payload[^3]. The ledger secures the sequence of operations by calculating each record's hash from its own content combined with the hash of the preceding entry, producing a tamper-evident audit chain that invalidates any retroactive administrative database tampering[^17].

Tasks must run in isolated containerized environments with hard memory limits (8 GB RAM per worker). If a file exceeds the allocated memory ceiling or experiences a processing error during geometric parsing, the worker must cleanly terminate the task, reset the container status to EVALUATION_FAILED, release all file descriptors, and record a diagnostic log to the audit journal[^2].

Security configurations require that all network communication across external clients, the FastAPI application gateway, and backend database instances enforce TLS 1.3 encryption. Files stored in Supabase storage buckets must be encrypted at rest using AES-256[^2].

## **OpenBIM Interoperability and Ecosystem Integration**

BIM-Guard operates within the wider buildingSMART OpenBIM software ecosystem[^2]. Full ISO 19650 compliance requires seamless data exchange with third-party common data environments, computer-aided design (CAD) software, and Building Information Modeling authoring platforms without vendor lock-in[^4].

To maintain an open architecture, BIM-Guard implements three standardized buildingSMART interface protocols: the openCDE Foundation API, the openCDE Documents API, and the BCF REST API v3.0[^2]. Rather than forcing design teams to manually export and upload files through web forms, external CDEs (such as Autodesk Construction Cloud, Trimble Connect, and Dalux) can connect directly to BIM-Guard using openCDE service hooks[^2]. When an information container is committed to an external project repository, an automated webhook notifies BIM-Guard's /api/cde/documents endpoint[^2]. The platform ingests the container, executes the four-tier verification and validation pipeline, and returns the compliance disposition alongside detailed BCF issue packages directly to the host platform[^2].

| :-------------------------------- | :-------------------- | :------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------- |
| **openCDE Foundation API**        | v1.0[^8]              | /api/cde/versions /api/cde/profile                                   | Discovers service capabilities, supported API versions, and validates user authentication profiles[^2].         |

The bSDD integration client acts as a semantic bridge, resolving project-specific classifications and property names against international data dictionaries[^2]. During Tier 3 semantic validation, the engine extracts classification URIs declared in the IFC model (for example, Uniclass 2015 Pr or EF tables) and verifies them against the official bSDD schema[^2]. To maintain operational reliability during network interruptions, BIM-Guard utilizes a local cache of standard classification systems[^2].

The BCF REST API v3.0 interface allows architectural and MEP design teams working in applications like Revit, ArchiCAD, or BlenderBIM to query validation issues directly within their design viewports[^2]. When a design model is flagged for a code violation—such as an uninsulated pipe crossing a seismic joint (GC-001) or incompatible metals causing galvanic corrosion risks (CC-001)—the designer receives an actionable BCF topic[^2]. Clicking the topic navigates the authoring software's camera to the exact spatial coordinate, isolates the affected components using their IFC GUIDs, and displays the corrective measures required to satisfy the project information requirements[^2].

## **Strategic Implementation Conclusions**

Achieving ISO 19650 compliance elevates BIM-Guard from an automated compliance checking script into an enterprise-grade digital information gatekeeper[^2]. By decoupling physical file names from mutable operational metadata[^11], enforcing a four-state CDE workflow machine through database-level triggers[^2], deploying a four-tier automated exchange verification pipeline[^2], and incorporating security-minded information triage and dynamic redaction[^9], the platform guarantees that digital assets remain verifiable, legally defensible, and reliable throughout the project lifecycle[^3].

The operational realization of this specification follows a phased implementation path: The initial phase focuses on the Supabase PostgreSQL database architecture, deploying migration scripts that establish the decoupled container metadata schema, CDE state machine enums, and row-level security policies[^2]. The second phase delivers the core ingestion gatekeeper, activating the 7-field National Annex file naming parser and the automated buildingSMART IDS 1.0 validation engine[^8]. The third phase deploys the openCDE Foundation, Documents, and BCF REST API v3.0 endpoints, enabling bi-directional federation with external CDE platforms and design authoring tools[^2]. The final phase integrates ISO 19650-5 security controls, implementing dynamic IFC geometry and semantic entity redaction alongside cryptographic audit chaining[^9].

By completing this technical implementation, BIM-Guard establishes an automated OpenBIM delivery pipeline that minimizes manual review overhead, eliminates versioning ambiguity, and enforces technical, operational, and security compliance across all asset delivery milestones[^3].
